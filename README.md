# DealLens

> An evidence-backed commerce intelligence agent that tracks the same product across sellers, builds an evidence-backed price history, and explains whether today's price is actually good, based on the data it has observed.

**"Don't just tell me the cheapest price. Tell me what today's price means."**

SerpApi India Hackathon 2026 · **Track 4 — Commerce & Market Intelligence**

> **Status (4 Oct 2026):** scheduled collection is live on GitHub Actions; the first production run completed. Price history under the current Query Plan is just starting to accumulate, so DealLens currently makes current-market claims only. Its explanations are generated by deterministic templates; an optional LLM synthesis layer is designed (see [Runtime AI](#runtime-ai-what-is-and-is-not-implemented)) but not built.

---

## The problem

A shopper looking at a laptop listed at ₹72,790 cannot easily tell whether that is a good price:

- **The cheapest listing is not the whole story.** One low price says nothing about how prices at other sellers, or on other days, compare.
- **Product identity across sellers is hard.** "ASUS Vivobook 15" is a family of many SKUs with different specs and prices; listings for different variants are easily mixed up.
- **Historical context matters**, and it does not exist unless someone collects it repeatedly.
- **"Great deal!" labels are rarely backed by evidence.** Shoppers deserve to see what a conclusion is based on.

## The solution

DealLens watches a small **Watchlist** of exact laptop SKUs in India and:

1. Collects Google Shopping results through **SerpApi** on a fixed schedule (3 times a day).
2. Stores every response as **immutable evidence** (hash-checked, never overwritten).
3. Turns rows into **Observations**, attributes them to products with **deterministic exact-model matching**, and records why any row is excluded.
4. Builds a **price history** from repeated observations of the same product at the same sellers.
5. Computes **deterministic Claims** (lowest listed price, spread, changes since a date, observed low/high/average) that are only allowed when enough evidence exists.
6. Shows **Coverage** honestly: observed calendar days, runs, independent sellers and valid observations, next to every conclusion.
7. Explains the result in plain language, with every sentence citing the Claim it restates and every Claim traceable to the raw SerpApi response.

## Why SerpApi is essential (not incidental)

DealLens has no other data source. Every price it shows exists because a SerpApi call returned it.

| SerpApi API | Role in DealLens | Used for statistics? |
|---|---|---|
| **Google Shopping API** (`engine=google_shopping`, `gl=in`, `google_domain=google.co.in`, `location=Mumbai,Maharashtra,India`) | **Primary market source.** One bounded call per scheduled slot returns ~40 Indian listings with seller (`source`), title, listed price (`extracted_price`), seller-displayed old price (`old_price`), delivery and Google identifiers. | **Yes**: every Observation, Coverage figure and Claim comes from Shopping results. |
| **Google Immersive Product API** (`engine=google_immersive_product`, `more_stores=true`) | **On-demand investigation** of one listing's seller offers (total price, stock text), run manually from the CLI. | **No**: never scheduled, never mixed into statistics ([ADR 0002](docs/adr/0002-shopping-primary-immersive-supplementary.md)). |
| **Account API** | Free credit check before any paid call (credit guard). | — |

How a Shopping response becomes evidence:

- One broad Query Plan (`q="ASUS Vivobook 15"`) serves all three tracked SKUs, so **each slot costs exactly one credit**.
- The raw JSON is saved unmodified with DealLens's own UTC `fetched_at`, the `search_id`, the query parameters (never the API key) and a SHA-256 hash.
- Each `shopping_results` row becomes an Observation; repeated observations across slots form the price history.
- Facts learned from live SerpApi responses are encoded as rules, for example: `extracted_old_price` returned the discount percentage (`11`) instead of the old price, so DealLens parses `old_price` itself; `product_id` turned out to be a Google catalog cluster, so it is kept as provenance only ([ADR 0004](docs/adr/0004-google-ids-are-provenance-not-identity.md)).

Research notes on the API, from SerpApi's own documentation and live tests, are in [docs/research/serpapi-google-shopping-india.md](docs/research/serpapi-google-shopping-india.md).

## What is implemented

| Feature | Notes |
|---|---|
| Watchlist | 3 provisional SKUs: `X1504VAP-BQ224WS`, `X1504MA-BQ832WS`, `X1504VA-NJ2324WS` ([config/products.json](config/products.json)) |
| Versioned Query Plans | `vivobook15-broad@2` active; `@1` retired and kept for provenance ([config/query_plans.json](config/query_plans.json)) |
| Google Shopping collection | `deallens collect`, one budgeted call per plan per run |
| Deterministic product identity | Brand + exact model key, hand-confirmed aliases, token-boundary matching |
| Seller normalization | Storefront → Seller map; Related Storefronts (e.g. Flipkart / Shopsy) count once until proven independent |
| Inclusion rules | Every excluded row keeps its reason: unmatched, ambiguous, cross-border, used/refurbished, unpriced, non-INR, indistinguishable in run, outlier, orphan raw, integrity failed, development probe |
| Immutable evidence + Run Manifests | Write-once, atomic, SHA-256 verified; every attempted call recorded as succeeded / repeat / failed / skipped |
| Coverage-gated Claims | Deterministic templates with claim IDs and full provenance |
| Evidence Ledger | Every observation, included or excluded, with reasons, `search_id`, raw path and timestamp |
| Streamlit UI | Read-only: market snapshot, product detail, current market, deal intelligence, observed price points, coverage, evidence, ledger |
| Scheduled collection | GitHub Actions, 09:00 / 15:00 / 21:00 IST |
| Credit safety | Single `CallBudget` gate, 60-credit floor, max calls per run, no retry after timeouts |
| On-demand Immersive investigation | CLI only; raw responses stored privately; sanitized view for display |

Not implemented: user accounts, alerts, price prediction, fuzzy matching, a runtime LLM, a public deployment.

## How DealLens avoids misleading conclusions

Coverage is computed only from **included** observations of **one Query Plan version**, from runs with a valid Run Manifest:

| Coverage Level | Condition | Claims allowed |
|---|---|---|
| **No history** | fewer than 2 runs or 1 observed calendar day | current market only: lowest listed price, spread, seller count, seller-displayed list prices. Summary ends "No price history yet." |
| **Limited history** | ≥ 2 observed calendar days and ≥ 2 runs | + per-seller "listed price moved from ₹X on day A to ₹Y on day B" |
| **Sufficient history** | ≥ 5 observed calendar days and ≥ 8 runs and ≥ 2 independent sellers | + observed low / high / average |

These thresholds are a product policy ([config/coverage.json](config/coverage.json)), not a statistical guarantee, and the UI says so.

Always shown: observed calendar days (counted in IST), runs, independent sellers and valid observations. Calendar days count *dates with observations*, not elapsed duration.

Never produced (a final guard rejects the wording): "all-time low", "fake discount", "best deal", "guaranteed", or any future-price statement. A seller-displayed list price is shown as **"shown by seller, not verified by DealLens"**. Stock is **"unknown"** because Shopping results do not state it, so DealLens says "lowest *listed* price", never "lowest *available* price". Observations from development probes, orphan raws or raws that fail their integrity check stay visible in the ledger but never count.

## Product identity and matching

Price history is only meaningful if every point is the same SKU. DealLens therefore:

- defines a product as **brand + exact model key** (e.g. `X1504VAP-BQ224WS`), with a small hand-confirmed alias list;
- matches a listing only if an alias appears as a whole run of title tokens (so `X1504VA` never matches `X1504VAP`, and invisible characters are stripped);
- classifies the outcome deterministically: **0 candidates → unmatched, 1 → matched, >1 → ambiguous** (ambiguous rows are never attributed);
- uses **no fuzzy, embedding or LLM matching** ([ADR 0003](docs/adr/0003-deterministic-matching-only.md)): a missed match stays visible as `unmatched`, while a wrong match would silently corrupt history;
- treats Google `product_id` / `headlineOfferDocid` as provenance only, after live tests showed identical listings with different ids and one id spanning different prices.

## Architecture

```
                     GitHub Actions (cron, 3 IST slots)          Streamlit UI (read-only)
                                 │                                      │
                                 ▼                                      ▼
  config/*.json ──► cli (composition root) ──────────────────►  public ─► ProjectionReader
  (Watchlist, Query Plans,    │                                             ▲
   Seller Map, rules,         ├─► collector ──► serpapi.CallBudget ──► HttpSerpApi ──► SerpApi
   coverage, collector)       │        │          (credit guard)           Google Shopping
                              │        ▼
                              │   evidence (Evidence Store: raw JSON + Run Manifests, write-once, SHA-256)
                              │        │
                              ├─► market.build_ledger ──► Ledger (Observations, Match, Inclusion)
                              │                               │
                              ├─► analysis.analyse ──► Coverage → Claims → template summary
                              │                               │
                              └─► projection.rebuild ──► SQLite (disposable read model) ─┘

  investigation (CLI only) ──► CallBudget(1) ──► Immersive Product API ──► private raw + sanitized offers
```

Module boundaries are enforced by tests: `domain`, `market` and `analysis` import no infrastructure; only `cli` reads environment variables or constructs the live SerpApi adapter; the Streamlit app may import only `deallens.public`, `deallens.projection`, `deallens.text` and `deallens.app` ([tests/test_architecture.py](tests/test_architecture.py)). Design details: [docs/codebase-design.md](docs/codebase-design.md), [docs/domain-model.md](docs/domain-model.md), [GLOSSARY.md](GLOSSARY.md), [docs/adr/](docs/adr/).

## Data flow

```
Watchlist + Query Plan → SerpApi Google Shopping → raw evidence + Run Manifest (immutable)
  → parsing / normalization → deterministic matching → inclusion reasons → Ledger (Observations)
  → analysis (Coverage, Claims, summary) → projection (SQLite) → Streamlit UI
```

Raw JSON plus Run Manifests plus versioned configuration are the **source of truth**. The SQLite projection is disposable: `deallens rebuild` regenerates it deterministically from evidence at any time ([ADR 0001](docs/adr/0001-raw-responses-are-source-of-truth.md)).

## Scheduled collection

[.github/workflows/scheduled-collector.yml](.github/workflows/scheduled-collector.yml):

| IST slot | UTC cron |
|---|---|
| 09:00 | `30 3 * * *` |
| 15:00 | `30 9 * * *` |
| 21:00 | `30 15 * * *` |

- Each run resolves its explicit IST slot from the cron (`deallens slot`) and calls `deallens collect --trigger scheduled --target-time <slot>`: **one bounded Shopping call per slot**.
- GitHub may start a scheduled run late or occasionally skip it. A late run keeps its slot; `fetched_at` records the actual time. Skipped slots are not back-filled.
- Duplicate protection: the slot is normalized to IST, the Run Manifest is write-once, and any time outside the three configured slots is refused before the credit check.
- `concurrency: deallens-scheduled-collector` (no cancel) prevents overlapping runs.
- Evidence is persisted **outside git**: chained between runs with the Actions cache and kept for 30 days as a run artifact (`deallens-evidence-<run_id>`).
- `SERPAPI_API_KEY` comes from GitHub Actions Secrets and is exposed only to the collect step.
- `max_attempts = 1`: a timed-out request may already have been billed, so it is not retried.

Budget for a 7-day collection: 3 slots × 7 days = **21 credits**, with collection stopping automatically below 60 remaining credits.

## Privacy and security

- `SERPAPI_API_KEY` lives only in `.env` (gitignored) or GitHub Secrets; the live adapter redacts it from every repr, log and error; tests scan written files and logs for it.
- Gitignored: `.env`, `data/evidence/raw/` (raw responses contain SerpApi account/archive URLs), `data/private/`, `data/projection/`, `data/cache/`.
- Immersive raw responses (which contain reviewer names and review text) are written only to `data/private/` and never reach the projection or the UI; the projection lists shareable sources only (regression-tested).
- The UI is read-only and never constructs a SerpApi client, even when a key is present ([ADR 0005](docs/adr/0005-public-mode-never-constructs-serpapi.md)).
- Test fixtures are trimmed copies of the 3 Oct 2026 probe responses with all SerpApi URLs and reviewer data removed ([tests/fixtures/README.md](tests/fixtures/README.md)). SerpApi's Terms on redistributing results have not yet been verified, so the repository is kept private.

## Local setup

```bash
git clone https://github.com/akifdaud0786/deallens.git
cd deallens
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -e ".[dev,ui]"
cp .env.example .env                 # then set SERPAPI_API_KEY (only needed for live commands)
```

Run the tests (no network, no credits):

```bash
pytest
```

The workflow tests use PyYAML and are skipped if it is not installed (`pip install pyyaml`).

Build the projection and open the UI:

```bash
python -m deallens.cli rebuild
streamlit run src/deallens/app/main.py
```

A fresh clone has no evidence (raw responses are not in git), so the UI shows "No observations collected yet." To view collected data, download a `deallens-evidence-<run_id>` artifact from the Actions tab, extract it into `data/` (it contains `evidence/`, `private/` and `projection/`), then run `rebuild` again.

Other commands:

| Command | Network | Cost |
|---|---|---|
| `python -m deallens.cli ledger [product_key]` | no | free |
| `python -m deallens.cli slot --cron "30 3 * * *"` | no | free |
| `DEALLENS_MODE=live python -m deallens.cli credits` | Account API | free |
| `DEALLENS_MODE=live python -m deallens.cli collect --trigger manual` | Google Shopping | 1 credit |
| `DEALLENS_MODE=live python -m deallens.cli investigate <observation_id>` | Immersive Product | 1 credit |

Live commands require both `DEALLENS_MODE=live` and `SERPAPI_API_KEY`.

## Limitations and honest scope

- Historical insights require accumulated observations; history under `vivobook15-broad@2` started with the first scheduled run on 4 Oct 2026.
- Google Shopping returns one page (~40 results) for one query; DealLens does not see the whole market.
- Stock status is unknown in Shopping results.
- Cross-border reseller handling is conservative (non-INR `alternative_price` or a small documented storefront list).
- The three SKUs are provisional and all belong to one product family.
- Immersive investigation is supplementary and manual.
- Not implemented: price prediction, fuzzy matching, user accounts, alerts, runtime LLM, public deployment.

## Runtime AI: what is and is not implemented

- **Implemented:** deterministic analysis. Every number is computed by code, and every summary sentence restates a numbered Claim with full provenance.
- **Designed, not built:** an optional LLM adapter that would only rewrite approved Claims, be validated against them, and fall back to the template on failure ([docs/codebase-design.md](docs/codebase-design.md) §2, `analysis`). The domain already records `summary_source` (`template` | `llm`).
